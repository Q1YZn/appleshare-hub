# AppleShare Hub 费用与调用优化

## 1. 当前设计

- Cron Worker `appleshare-hub-cron` 每 5 分钟醒来一次，并发抓取全部渠道，把完整快照写入 R2 的 `snapshot/latest.json`，随后退出。
- 用户访问 `GET /api/accounts` 时只读 R2 快照，不请求任何上游。
- `/api/accounts` 响应写入 Cloudflare 边缘缓存，`Cache-Control` 为 `public, max-age=300, s-maxage=300`。
- 前端默认每 300 秒轮询一次；页面隐藏时暂停，回到前台再拉取。

这里没有“长期开着的 Worker”。Cron Worker 只在触发时短暂运行，其余时间不占用资源，也不存在按小时计费的常驻进程。

## 2. 免费额度

| 项目 | 免费额度 |
| --- | --- |
| Workers / Pages Functions | 10 万次请求/天 |
| Workers 标准版 | $5/月，含 1000 万次请求与 3000 万 CPU-ms，超出请求 $0.30/百万次 |
| R2 Class A 写入 | 100 万次/月 |
| R2 Class B 读取 | 1000 万次/月 |
| R2 存储 | 10 GB-month，删除免费 |

## 3. 10 万用户测算

假设 10 万用户、每人停留 10 分钟、一个月内分散访问：

### 未优化：前端每 30 秒轮询

- 每人约 20 次请求，共约 200 万次/月。
- 平均每天约 6.7 万次，刚好在 10 万次/天免费额度内。
- 如果 10 万人在同一天集中访问，单日 20 万次会超限，没有余量。

### 优化后：300 秒轮询 + 边缘缓存

- 每人约 2 次请求，共约 20 万次/月，平均每天约 6,700 次。
- 只有缓存过期后的少数请求会真正执行 Functions；5 分钟窗口内其他请求由 Cloudflare 边缘缓存直接返回。
- 手动刷新按钮只重新请求 `/api/accounts`，不会触发上游抓取，因此也不会放大费用。
- Cron Worker 每月约 8,640 次调用，R2 每月约 8,640 次写入，都在免费额度内。

结论：10 万用户、每人停留 10 分钟的规模下，优化后免费额度足够，实际费用接近 $0。

## 4. 已落地的优化

1. 轮询间隔从 30 秒改为 300 秒，请求量直接降到原来的 1/6。
2. `/api/accounts` 使用 Cloudflare Cache API 写边缘缓存，缓存命中不执行 Functions。
3. 页面不可见时停止定时器，回到前台才重新拉取。
4. 手动刷新只绕过浏览器缓存，仍优先命中边缘缓存，不直接打 R2/上游。
5. 上游抓取固定由 Cron Worker 每 5 分钟执行一次，用户请求永远只读快照。

## 5. 还可以继续压

- 进一步把 TTL 提高到 10-15 分钟：账号本来就是历史数据，延迟几分钟影响很小。
- 增加 `stale-while-revalidate`：缓存过期时先返回旧快照，后台再刷新，用户感知延迟更低。
- 前端只在首次进入、切回页面或用户点击刷新时请求，去掉自动轮询；代价是停留期间数据不会自动更新。
- 给接口加 ETag/304，减少重复下载流量。
- 后续如果规模确实超过免费额度，再升级 Workers 标准版，$5/月包含 1000 万次请求，对当前量级仍有极大余量。

## 6. 风险边界

最极端情况是 10 万人在同一分钟、从大量不同地区同时访问，且缓存全部刚过期。此时会有一批请求真正执行 Functions，单日可能短暂接近免费上限。对于这种场景可以再加限流、Turnstile 或把 TTL 调大；按正常使用规律，这个概率很低。
